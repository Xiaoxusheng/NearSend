# 关键决策记录

记录开发过程中做出的、会影响后续维护的决策及其理由。
每条都包含「考虑过的替代方案」与「放弃了什么」，便于日后重新评估。

---

## D1. 前端框架使用 React 而不是 Vue 3

**背景**：任务书建议 Vue 3 + Ant Design Vue + Pinia；但会话中用户明确要求「使用 React」。

**决策**：React 19 + TypeScript + Vite 8 + Ant Design 6 + Zustand。

**理由**：以用户的直接指令为准。生态对应关系清晰：

| 任务书 | 本项目 | 说明 |
| --- | --- | --- |
| Vue 3 | React 19 | — |
| Ant Design Vue | Ant Design 6（React 版） | 同为 antd 设计语言 |
| Pinia | Zustand | 同为轻量 store，API 更小 |
| Vue Router | React Router 7 | — |
| Vite | Vite 8 | 不变 |

**放弃**：任务书里对 Vue 生态的具体写法描述。

## D2. 采用「服务端中转」而非点对点

**决策**：文件先上传到运行服务的机器，再由接收方下载。

**理由**：浏览器无法监听端口、无法扫描局域网、无法接受入站连接。
WebRTC DataChannel 虽然可以实现点对点，但**仍然需要信令服务器**，
且在无 STUN 的纯局域网中需手工交换 SDP，复杂度与收益不成比例。

**代价（已在 README 与架构文档中如实说明）**：

- 服务端磁盘占用约为传输总量；
- 传输速度受服务端磁盘与网络限制；
- 不是「纯点对点」。

**放弃**：真正免中转的点对点传输（需要原生客户端）。

---

## D3. 不做伪造的「局域网自动发现」

**决策**：设备列表只显示**真实连接到本服务**的客户端。

**理由**：任务书明确要求「不能为了展示自动发现效果而伪造设备」。
浏览器的安全模型不支持任意局域网扫描，这是不可绕过的约束。

**替代方案**：设备通过扫码/输入地址打开页面即自动登记，用户感受上接近「自动出现」。

**为后续留的口子**：发现能力与 Web 注册机制**解耦**——设备与会话模型不依赖任何发现协议，
后续加一个用 mDNS/DNS-SD 的原生守护进程时，只需让它调用登记接口即可。

## D4. 传输槽位：只有 `uploading` 才接受分块

**决策**：`queued` 状态的分块上传返回 `too_many_concurrent`。

**理由**：最初允许 `queued` 也能上传（为了降低前端复杂度），
但那样排队任务只要能发分块就等于**绕过了并发上限**——限制形同虚设。

**代价**：前端必须等 `transfer.queued { granted: true }` 才能开始上传。
这个事件语义被明确拆成两种：`waiting: true`（仅排队）/ `granted: true`（可上传）。

**踩过的坑**：前端最初要求「本地状态已是 `uploading`」才启动上传器，
而事件到达时本地状态往往还停在 `queued`，导致**上传永远不启动**。
现在改为「收到 granted 就启动，由上传器自己向服务端确认分块状态」。

## D5. 取消任务保留已传分块

**决策**：`Cancel` 不清空临时数据，只把状态改为 `cancelled`；清理交给保留期巡检。

**替代方案**：取消即删除临时文件（更省磁盘）。

**理由**：大文件传到 90% 时取消，如果直接丢弃，重试要从头再来，
与「支持断点续传」的产品目标冲突。保留后重试只需补缺失分块。

**代价**：取消的任务会占用一段时间的临时磁盘空间。
由 `tempRetentionHours`（默认 24 小时）与「已完成任务立即回收」共同控制。

---

## D6. 清理策略严格按状态区分

**决策**：

| 状态 | 临时数据 |
| --- | --- |
| `uploading` / `queued` / `paused` / `awaiting` | **永不清理** |
| `completed` | 立即回收（分块已提交，只剩空目录） |
| `failed` / `cancelled` / `rejected` | 超过 `tempRetentionHours` 后清理 |

**理由**：清理逻辑最容易造成「误删正在进行中的任务」。这里宁可留下临时文件，
也不冒险删除活跃数据；数据库异常时同样保守跳过。

**同时**：`historyRetentionDays` 只影响记录可见性，`/api/history/clear` 只标记
`history_visible = 0`。**任何自动逻辑都不删除接收目录中的用户文件。**

---

## D7. 权限模型：本机回环 + 显式信任，不做「首次自动放行」

**决策**：特权只来自 (a) 请求源为回环地址，或 (b) 设备已被显式授予信任。

**替代方案 A**：任何设备都能改设置（最简单，也最危险）。
**替代方案 B**：没有受信任设备时自动放行第一个认领者（做过，已移除）。

**理由**：方案 B 在共享局域网里等于让任意陌生人取得管理权限。
这个「便利」无法用任何本地证据交换。

**代价**：服务跑在无头机器上时，需要从另一台电脑输入管理令牌。
令牌在首次启动时打印在控制台并写入数据目录，代价可接受。

**这也影响了测试**：所有从 `127.0.0.1` 发出的测试请求都是特权设备，
因此**跨设备授权测试必须通过局域网 IP 建立会话**，否则会假通过。
`scripts/e2e_test.py` 已按此实现（自动探测局域网地址）。

## D8. 下载使用 120 秒短期票据而不是会话令牌

**决策**：`POST .../ticket` 签发绑定「任务 + 文件 + 设备」的短期票据，
`GET /api/download?ticket=` 使用它。

**理由**：浏览器原生下载无法携带自定义请求头。把会话令牌放进 URL 会进入
访问日志、浏览器历史与 Referer。票据是单一用途、短时效的替代品，
即使泄露也无法用于其它任务或接口。

**放弃**：用 `fetch` + Blob 下载可控性更好，但会把整个文件读进内存并失去
Range 续传能力，对大文件不可接受。

## D9. WebSocket 令牌走首帧而不是 URL

**决策**：连接建立后客户端必须在 8 秒内发送 `client.hello { token }`。

**理由**：浏览器无法为 WebSocket 设置请求头；URL 查询串会被各类中间件与
访问日志记录。首帧握手把令牌限制在加密无关的连接体内，且不进入任何日志。

**代价**：握手多一个往返；服务端需要为「已连接但未鉴权」的 socket 设置超时。

## D10. SHA-256 三级降级实现

**决策**：Web Crypto → Web Worker 池 + 纯 JS → 主线程纯 JS（分片让出）。

**理由**：`crypto.subtle` 只在安全上下文可用，而局域网访问是明文 HTTP
（`http://192.168.x.x`，非 localhost）。**只依赖它会让分块校验在真实部署中静默失效。**

纯 JS 实现单核会成为千兆局域网的瓶颈，因此放进 Worker 池并行；
Worker 被 CSP 拦截时退回主线程分片计算，至少保证界面不卡死。

**代价**：多约 300 行哈希代码 + 一个 Worker 文件；CSP 需要放行 `blob:`。

**验证**：诊断页用公开测试向量自检两条实现路径，并如实显示当前使用的实现。

## D11. SQLite 单连接串行化

**决策**：`SetMaxOpenConns(1)` + WAL + `busy_timeout(10000)`。

**替代方案**：多连接 + 应用层写锁（更复杂，容易漏加锁）。

**理由**：所有数据库操作都是微秒级短事务。串行化的读性能损失在局域网规模下
完全不可感知，换来的是「绝不出现 `SQLITE_BUSY`」的确定性。
真正耗时的 I/O（分块读写、下载流式响应）全部在数据库连接之外完成。

**放弃**：理论上的读并发。

---

## D12. 重名默认「自动重命名」，且 `neverOverwrite` 兜底

**决策**：默认 `rename`，生成 `报告 (1).pdf` 形式；
`fsutil.UniqueName` 的 `neverOverwrite` 标志确保即使策略是 `overwrite`，
在特定路径（竞态重试）下也改为改名。

**理由**：任务书明确「不默认覆盖已有文件」。自动重命名是唯一既不丢数据
又不需要用户干预的策略。

**同时**：提交前会**重新解析**目标路径，因此即使「接受」之后出现了新的同名文件，
也不会发生静默覆盖。

## D13. 僵死任务回收（10 分钟无进展）

**决策**：`uploading` / `verifying` 状态且 `updated_at` 超过 10 分钟未刷新 → 标记为
`failed`（保留 `resumable`）并释放槽位。

**理由**：发送方关闭浏览器、断网或宕机后，任务会永远停在 `uploading` 并占着一个槽位，
最终把并发上限吃光（表现为「所有新任务都在排队且传不动」）。
这是压力测试中真实观察到的问题。

**判定依据**：`updated_at` 在每次分块落盘时刷新，是真实的存活信号，
而不是「有没有收到心跳」这类不可靠的指示。

**不回收 `queued`**：等待是其正常状态，且不占槽位。

## D14. 设备名称去重，但名称仍不作为身份

**决策**：登记会话时若名称已被占用，追加 `(浏览器)` / `(系统)` 后缀。

**理由**：同一台机器上打开多个浏览器（或移动端模拟）会得到相同的默认名，
用户无法区分。这是 UI 可用性问题，不是安全问题。

**边界**：设备身份始终是随机会话 ID。名称只用于展示，
`isPrivileged` 等判定都不读名称。

## D15. 测试脚本复用 TCP 连接

**决策**：`scripts/e2e_test.py` 用自实现的连接复用客户端，而不是 urllib 的一次一连接。

**理由**：在 Windows + 虚拟网卡/代理过滤驱动的环境下，
高频「连接 → 大数据传输 → 关闭」交替会偶发 `ConnectionResetError`，
与环境有关而非服务端缺陷（Go 自身的测试用连接复用，同样场景数千次零失败）。

同时，**浏览器也会复用连接**，所以复用连接的测试更贴近真实行为。

**通用教训**：本机测试必须显式禁用系统代理（Go 的 `ProxyFromEnvironment`、
Python 的 `ProxyHandler({})`），否则会得到 `502 upstream connect failed` 这类假故障。

---

## D16. 错误响应前必须丢弃请求体

**决策**：分块上传的失败分支在写响应前 `io.Copy(io.Discard, ...)` 掉剩余请求体。

**理由**：分块体可达数十 MiB，而「状态非法 / 无权限」的判定发生在读 body 之前。
直接写响应会让客户端在发送途中收到连接重置，**浏览器只能显示无法解释的网络错误**，
而不是我们精心设计的错误码与文案。

**验证**：`scripts/e2e_test.py` 中有一个带真实大请求体的非法请求用例专门覆盖它。
